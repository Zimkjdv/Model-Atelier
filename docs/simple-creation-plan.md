## 1. 目標與評估結論

平台已具備本機 ComfyUI、Pony／Animagine、LoRA、結構引導、SDXL 圖片風格參考及特定 FLUX 流程。現況較接近有經驗使用者的創作與實驗工作台；下一步應優先讓新手能透過完整範例完成第一次創作，而非持續增加技術選項。

核心驗收目標：**已完成必要安裝的新手，能否盡量不展開技術參數，完成選範例、生成、保存及修改再生成。**

「第一次成功」包括流程可執行、結果可理解及作品可保存，不承諾每次都產生完美人物、精確角色或完全相同畫風。缺少模型或元件時，成功體驗應是清楚知道缺少什麼及下一步，而非遇到無法理解的停用按鈕。

本次分析依據前後端程式、模型配置、功能文件、導覽與既有介面截圖。分析期間未重新執行 GPU 生成、訓練或新手使用測試。歷史實測僅適用於原紀錄的模型、配置、題材及環境。

## 2. 模型與技術描述應修正的期待

- 不使用「目前絕對霸主」「全面碾壓」「完美複製任意畫風」作為平台承諾。動漫角色、畫風、文字遵循、多人構圖與硬體成本需要分開評估。
- Pony V6 XL 與 Animagine XL 為 SDXL 生態的模型選擇；平台目前固定選用 Animagine XL **4.0 Opt**，不可將不同版本混稱為同一驗收對象。
- FLUX.1 Kontext Pro 不等於本機開放權重的動漫微調模型。平台現有 FLUX 主路線為 **FLUX.1 [schnell]**，不是 Kontext Pro，也不代表支援整個 FLUX 家族。
- 官方已有 FLUX.2，不應把 FLUX.1 宣稱為 2026 年最新架構。
- LoRA、IP-Adapter、ControlNet 的目的不同：分別提供權重調整、圖片條件與結構約束，不能視為可互換的畫風複製工具。
- 本機執行、開放權重、技術可用及授權條件是不同概念，不使用「開源本機＝無任何限制」的描述。
- 12GB VRAM 只能作為部分已測環境背景，不能當成所有模型、解析度及附加元件都能執行的保證；CPU 卸載也涉及系統 RAM 與耗時。

建議定位：**提供可重用、可追溯的動漫創作與風格控制流程。**

- [BFL 官方 FLUX.1 儲存庫](https://github.com/black-forest-labs/flux)
- [BFL FLUX.2 官方介紹](https://bfl.ai/blog/flux-2)
- [Animagine XL 4.0 官方模型卡與提示指南](https://huggingface.co/cagliostrolab/animagine-xl-4.0)

## 3. 功能存在，不代表能任意組合

### 3.1 現況與限制

| 能力 | 目前基礎 | 必須呈現的限制 |
| --- | --- | --- |
| 本機生成 | Vue／FastAPI 操作獨立 ComfyUI，資料保存在本機 | 平台可開啟不等於引擎在線或模型可生成 |
| Pony V6 XL | 固定模型資料、專用起始預設及歷史生成驗收 | 風景驗收不能直接證明人物、手部與角色品質 |
| Animagine XL 4.0 Opt | 固定來源、專用預設及歷史生成驗收 | 換版本、題材或附加元件後需分別判定 |
| 一般 LoRA | 支援流程可使用最多四個有序 LoRA | SDXL 架構相同不保證特定基底的視覺效果相同；不得混用 SDXL 與 FLUX LoRA |
| 結構引導 | Canny、Pose、Depth 專用流程 | 節點、控制模型、基底與條件要匹配；不是任意流程的通用勾選項 |
| SDXL IP-Adapter | 單張畫風／角色外觀參考 | 首版不組合 LoRA、多圖、FaceID、Canny 或局部編輯；不保證身份鎖定 |
| FLUX Schnell | 文生圖、固定 PVC LoRA、獨立 VAE 圖生圖 | 固定擴充配置；LoRA＋圖生圖混用、多 LoRA、Redux、身份參考及未知組合未開放 |
| 自訓 LoRA | 資料審查、準備、執行、產物與評估流程 | 固定 Animagine 4.0 Opt 基底；技術訓練通過不等於畫風或角色品質通過 |

### 3.2 介面實作原則

- 依「流程＋模型／元件組合」判斷能力，不依「模型清單裡有這個檔案」宣告全部可用。
- 範例卡只列該模板支援的操作與比例；未支援的組合停用並提供具體原因。
- 簡易模式不能因為隱藏參數而略過原有預檢、元件核對或提交時驗證。
- 不能缺少 LoRA 就靜默移除、缺少參考元件就退回普通文生圖，或自行換成另一個模型。
- 讓使用者看到「此範例缺少影像編碼器 → 查看安裝方式」，詳細 hash、節點版本與歷史證據放入展開區。
- 「可使用」僅表示目前可用性檢查結果，不能表示品質已驗證、授權已核實或本機一定不會記憶體不足。

依據：[平台總覽](../README.md)、[LoRA](models/lora-library.md)、[IP-Adapter](models/ipadapter-reference.md)、[FLUX 擴充](models/flux-extensions.md)、[專用格式邊界](specialized-workflow-formats.md)。

## 4. 現有介面的評估

目前五種創作目的、左側輸入／右側預覽、收合進階參數及清楚的生成按鈕，方向合理。主要問題不是畫面本身過度擁擠，而是新手仍需自行作出許多技術選擇。

| 操作負擔 | 改善方向 |
| --- | --- |
| 使用者先理解 Checkpoint／SDXL／FLUX 才能選入口 | 先選想完成的範例，模型作為次要說明 |
| 選模型後仍需補提示詞、負面提示詞與參數 | 提供完整配方，而非只提供取樣參數預設 |
| FLUX 要自行選擇四個元件 | 由固定模板解析相容元件，顯示就緒狀態與缺項 |
| 生成後還需找任務資訊或到作品庫匯入 | 在成果旁提供「存入作品庫」「再畫一張」「帶入設定修改」 |
| 相容性與歷史證據文字較多 | 主要區域顯示結論及處理入口，詳情按需展開 |

成果操作沿用既有任務與作品保存機制。已存入作品庫時應顯示已保存狀態，避免重複匯入造成困惑。

## 5. 第一次就成功畫出動漫圖片：導覽改善

現有 [HTML 導覽](guide/index.html)對五種目的、模型分類、生成／匯入區別、FLUX 限制及訓練階段大致符合實作。它目前較適合完整操作查閱，仍缺少一條從範例到真實成果的入門路線。

### 5.1 優先補齊的內容

1. 在前段加入「完成第一張動漫圖片」，將必要安裝前置條件與日常四步創作分開。
2. 提供三個完整模型配方：明確模型版本、正負面提示詞、Seed、尺寸、取樣設定及必要元件。
3. 在簡易模式尚未完成前，先教使用者操作現有「套用模型預設」，說明它帶入哪些欄位、保留哪些內容。
4. 補上可直接複製的英文提示詞與中文解說，不只放一段中文風景描述。
5. 加入真實生成成果與原始設定，讓使用者知道合理的預期效果。
6. 保留既有介面操作截圖及示範資料標示，不把色塊、合成素材或空狀態畫面當成模型畫質證據。
7. 在範例入口清楚標示 FLUX Schnell 與實際限制，不把關鍵條件藏在頁尾。
8. 關鍵入門說明直接置於 HTML；深入 Markdown 連結可保留，但不能要求一般讀者開啟原始 Markdown 才能完成第一張圖。
9. 加入「結果不像範例」的判讀順序：模型版本、模板修改、提示詞語言、必要元件、Seed／尺寸與環境差異。

### 5.2 提示詞語言：中文介面不等於模型中文能力

目前標準流程將 `prompt` 與 `negative_prompt` 直接送入 `CLIPTextEncode`，沒有看到自動翻譯步驟。依據：[標準 workflow](../backend/workflows.py)。

**中文介面不代表模型具備同等中文理解能力。** Animagine 官方提供以英文標籤為主的提示方式；中文描述不能被當作穩定重現其效果的等價輸入。

第一階段建議：

- 模板保存實際送給模型的英文提示詞，另存中文解說，清楚區分兩者。
- 顯示「實際生成提示詞」；使用者修改中文說明時，不可讓他誤以為英文已自動更新。
- 初版可提供已整理好的中英對照選項，例如服裝、髮型、場景；僅對已支援選項作明確映射，不宣稱支援任意中文翻譯。
- 保留直接修改英文提示詞的入口；Pony 使用其專屬提示模式，Animagine 使用對應標籤，Schnell 使用經驗證的自然語句範例。
- 未提供翻譯時，於描述欄附近清楚說明，不等到生成失敗才告知。

後續若增加自動翻譯，需獨立規劃本機或雲端來源、成本、資料傳送與失敗處理。必須保留原文及實際送出文字，讓使用者預覽修正；不能翻譯 Seed、LoRA 觸發詞或模型專用標籤，也不能在失敗時假裝翻譯成功。本方案不預設啟用任何翻譯服務。

## 6. 統一預設參數的驗證摘要來源

### 6.1 原先辨識的不一致

[CreationStudio.vue](../frontend/src/CreationStudio.vue) 原 `presetValidationLabel` 對未啟用 LoRA、且非 Pony 專屬預設的情況，曾顯示概括的「起始參數，尚未逐模型實測」。但 [model_profiles.py](../backend/model_profiles.py) 的 Animagine 預設已有固定 RTX 3060、1024×1024、28 steps、單張風景與離線作品讀取的驗收說明。本輪已依 6.2 實作共同顯示來源，見 [presetEvidence.ts](../frontend/src/presetEvidence.ts)。

兩種文字的範圍原本未說清楚；現在摘要與詳情共用後端 `preset.validation`，另外呈現當前設定差異，不再用 Pony ID 特判。

### 6.2 改善實作

- 由共同的證據資料提供摘要與詳情，前端不再只用 Pony ID 特判是否已驗。
- 區分「一般起始參數」「固定歷史配置已驗」「目前設定已修改」「目前檔案未驗證」等概念；歷史已驗與當前檔案未知可以同時存在。
- 摘要交代題材、配置及硬體範圍，例如「歷史已驗：RTX 3060／1024² 風景；目前檔案仍需核對」。
- 比對目前模型、元件與設定是否匹配證據；修改尺寸、取樣、LoRA 或題材時，不沿用原範例的品質結論。
- 登記 SHA256 匹配不能宣稱已讀取並驗證當前權重檔。
- 無資料或資料過期時顯示未知／待更新，不推定失敗或通過。

驗收至少涵蓋 Pony、Animagine、一般 SDXL、未知模型、啟用 LoRA 及修改參數；摘要與詳情不得對同一範圍作相反陳述。

## 7. 建立「簡易創作｜進階工作台」

### 7.1 入口與四步流程

創作入口提供 **簡易創作｜進階工作台**。第一次進入預設簡易創作，之後記住使用者選擇。從既有作品還原或專用流程入口進入時，仍應導向能完整承載原設定的工作台，不因偏好而丟失設定。

簡易模式只要求：

1. 選一張範例卡。
2. 使用原範例，或修改描述。
3. 選擇模板支援的比例。
4. 按生成，直接查看與保存成果。

模型、元件、取樣器、步數及負面提示詞等由模板提供。保留「查看完整設定」及「帶到進階工作台」。

### 7.2 共用底層流程

簡易模式是既有工作流程的簡化入口，不建立第二套生成系統。

- 共用現有預檢、生成提交、任務狀態、原請求恢復、素材處理與作品保存。
- 共用模型預設與能力判斷，避免兩種模式的參數或限制逐漸不同。
- 載入模板只填入設定，不自動提交 GPU 工作。
- 已有修改時沿用未保存保護，不能無提示覆寫。
- 帶到進階工作台時完整保留可支援的模板設定及來源。
- 專用流程的草稿／匯出／還原能力沿用既有限制，不宣稱所有模板都能透過一般 JSON 交換。
- 初版以完整單向轉交進階工作台為必要能力；若進階設定無法映回簡易模板，明確保留在進階模式，不靜默刪掉設定。

### 7.3 結果區與例外狀態

- 成果旁直接提供「存入作品庫」「再畫一張」「帶入設定修改」。
- 原範例維持固定 Seed；只有明確選擇「再畫一張」才更換 Seed。一般重新按生成不應暗中改變種子。

## 9. 第二階段：真正面向畫風控制的任務模板

**三個模型範例只能教「不同模型怎麼畫」，不能完整教「如何模仿特定畫風」。** 以下兩類任務現已加入簡易創作，固定組合與真實對照見開頭交付紀錄。

### 9.1 套用風格 LoRA

- 固定已驗基底、LoRA 版本、必要觸發詞、順序及模型／CLIP 強度。
- 提供相同提示詞、Seed 與取樣條件下的有／無 LoRA 真實比較。
- 簡易模式先開放經驗證的強度範圍；完整強度與有序串接留在進階工作台。
- 不因為檔案能載入就宣稱畫風效果成立；不同題材應確認泛化情況。

### 9.2 參考一張圖片的畫風

- 固定 SDXL 基底、IP-Adapter 及影像編碼器，使用既有單張畫風流程。
- 使用者主要選參考圖、描述與參考程度；其餘作用參數由模板提供。
- 若使用「低／中／高」參考程度，各檔需有可查看的確切參數及實測，不任意假設提高權重就更像。
- 說明參考可能連帶帶入服裝、髮色、姿勢或背景，不保證只抽出純畫風。
- 附參考圖、無參考對照與使用參考後的成果。
- 沿用首版限制，不暗中加入 LoRA、Canny、局部修補、多圖或身份鎖定功能。

兩種模板先沿用現有流程。未知組合需要另立開發及驗收工作，不能只增加介面開關就宣告支援。
